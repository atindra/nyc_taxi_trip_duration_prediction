## The 30-Second Summary

This project predicts how long a NYC taxi trip will take, given:

- pickup time & place  
- drop-off place  
- passenger count  
- that day's weather

Everything is generated synthetically, piped through a reproducible ML workflow, served via a FastAPI, and monitored for drift.

High-level flow:

```
raw CSVs → ingest → validate → train → save champion → serve API
              ↑           ↑         ↑
            DVC         DVC       MLflow
            tracks      tracks    logs
            versions    versions  runs
```

## The Data

The data is **fully synthetic**. It is generated by `scripts/create_sample_data.py` with a fixed random seed (`SEED = 7`), so every run produces the same 50,000 trips and ~180 weather days.

What the generator does:

```
random seed 7
     │
     ▼
weather: daily temp curve + rain/snow/clear/cloudy
     │
     ▼
trips: pickup times weighted toward rush hour
       random pickup coords inside NYC-ish box
       drop-off coords based on random distance/bearing
       duration = base + per-km × distance
                + rush-hour congestion
                + weekend/weekday offset
                + rain/precipitation penalty
                + random noise
     │
     ▼
corrupt ~1.5% of rows (bad GPS, invalid timestamps, etc.)
     │
     ▼
trips.csv + weather.csv
```

Why synthetic? No downloads, no secrets, fully reproducible, and it lets us intentionally dirty some rows so validation has real work to do.

## Code Modules: The Details

### `src/data/ingest.py`

This is the ETL loader. It:

1. Reads `trips.csv` and `weather.csv`.
2. Normalizes column names (lowercase, strip spaces, underscores).
3. Checks that required columns exist.
4. Joins weather onto trips by **pickup date**.
5. Writes `data/interim/ingested_trips.csv` plus a small JSON report with row counts.

### `src/data/validate.py`

This is the bouncer. It checks every row and rejects bad ones with a reason.

Rules include:

| Check | What fails |
|-------|------------|
| Timestamps parse | strings like `not-a-timestamp` |
| Coordinates inside NYC bounds | GPS outside the `40.4–41.1` lat / `-74.3– -73.6` lon box |
| Passenger count | not `1–6` |
| Trip duration | not `30–7200` seconds |
| Dropoff after pickup | dropoff ≤ pickup |
| Weather present | missing temp, precipitation, or weather category |
| Precipitation | outside `0–500` mm |
| Weather category | not one of `clear`, `cloudy`, `rain`, `snow` |

Invalid rows go to `data/quarantine/invalid_rows.csv` with a `validation_errors` column.
Valid rows go to `data/processed/validated_trips.csv`.

### `src/features/transform.py`

Turns raw inputs into model-ready features.

Features created:

| Feature | Meaning |
|---------|---------|
| `pickup_hour` | Hour of day (0–23) |
| `weekday` | Day of week (0=Monday, 6=Sunday) |
| `is_weekend` | 1 if Saturday/Sunday |
| `is_rush_hour` | 1 if hour is 7–9 or 16–19 |
| `hour_sin` / `hour_cos` | Cyclic encoding so hour 23 is close to hour 0 |
| `distance_km` | Haversine distance from pickup to drop-off |
| `pickup_longitude`, etc. | Raw coordinates |
| `passenger_count` | Number of passengers |
| `temp_c` | Temperature |
| `precipitation_mm` | Precipitation |
| `weather` | Categorical weather value |

It also has `chronological_split`, which splits data by time: oldest 70% train, next 15% validation, newest 15% test.

> The transformer is a sklearn `BaseEstimator`. It is **inside the saved pipeline**, so the API cannot accidentally use different feature math from training.

### `src/models/train.py`

The trainer builds three candidate pipelines:

```
Raw input
   │
   ▼
TaxiFeatureTransformer
   │
   ▼
ColumnTransformer
   ├─ numeric: median impute + scale
   └─ categorical: most-frequent impute + one-hot
   │
   ▼
Model (baseline / ridge / gradient boosting)
```

The three candidates are:

1. **Baseline** — always predicts the median trip duration.
2. **Ridge regression** — linear model with L2 penalty.
3. **HistGradientBoostingRegressor** — gradient boosting trees.

For each candidate the script:

- Fits on the training set.
- Computes MAE/RMSE on validation and test sets.
- Logs params, metrics, git sha, data hash, and the model to MLflow.
- Times the fit.

Then it picks the champion as the model with the **lowest validation MAE** (excluding the baseline), saves it as `models/champion.joblib`, and writes metadata.

### `src/api/app.py`

FastAPI service. Three endpoints:

| Endpoint | What it does |
|----------|--------------|
| `GET /health` | Returns `{"status": "ok"}` if the model loaded; otherwise HTTP 503. |
| `GET /v1/model/info` | Returns champion metadata (version, run ID, row counts). |
| `POST /v1/predict` | Takes a trip JSON, validates it, predicts duration in minutes. |

The API loads the champion model once when it starts. If the model file is missing, `/health` still answers but returns HTTP 503.

Every prediction is logged to `monitoring/predictions.sqlite` with:
- request ID
- timestamp
- model version
- input JSON
- predicted seconds
- latency in milliseconds

Input validation is strict. If you send a passenger count of `0` or coordinates outside NYC, you get HTTP 422, not a made-up number.

### `src/monitoring/monitor.py`

Computes drift between a reference window and a current window.

| Metric | Used for |
|--------|----------|
| PSI (Population Stability Index) | Numeric features: distance_km, pickup_hour, prediction_seconds |
| KS test | Same numeric features; p-value tells you if distributions differ |
| Chi-square | Categorical feature: weather |

### `src/monitoring/retrain_trigger.py`

Recommends retraining only if **all** three are true:

1. The new data passes validation.
2. At least 2 features have PSI > 0.25 (severe drift).
3. Labelled MAE is at least 20% worse than the champion's MAE.

Output is a JSON like:

```json
{
  "data_valid": true,
  "severe_drift": true,
  "performance_degraded": true,
  "action": "retrain_and_compare"
}
```

It recommends; it does **not** auto-deploy.

## DVC: Why It's Here

DVC (Data Version Control) is like `make` or Git for data pipelines.

`dvc.yaml` defines three stages:

| Stage | Input | Output |
|-------|-------|--------|
| `ingest` | raw CSVs + `ingest.py` | `data/interim/ingested_trips.csv` |
| `validate` | ingested CSV + `validate.py` | `data/processed/validated_trips.csv`, quarantine CSV |
| `train` | validated CSV + `transform.py` + `train.py` | `models/champion.joblib`, `models/model_metadata.json`, `experiments/comparison.json` |

`dvc.lock` stores MD5 hashes of every dependency and output. If you rerun `dvc repro` and nothing changed, DVC skips that stage. If you change the training code, DVC reruns training but not ingestion.

## MLflow & `evidence/`: Tracking & Reporting

### MLflow

MLflow tracks every training candidate as a "run." Each run stores:

- **Params**: model type, hyperparameters, number of training rows
- **Metrics**: validation MAE, validation RMSE, test MAE, test RMSE, fit time
- **Tags**: git commit hash, data hash
- **Artifacts**: the full serialized pipeline

You browse runs with:

```bash
.venv/bin/mlflow ui --backend-store-uri sqlite:///mlflow.db
```

Then open `http://127.0.0.1:5000`.

### `evidence/`

`evidence/` is the "report card" committed to git, so reviewers don't need MLflow open.

| File | What's inside |
|------|---------------|
| `evidence/comparison.json` | Metrics for all three models. |
| `evidence/model_metadata.json` | Champion name, MLflow run ID, target, feature list, row counts. |
| `evidence/mlflow-runs.csv` | Table of the latest run per model. |

You regenerate it with:

```bash
.venv/bin/python scripts/export_evidence.py
```

## Which Model Won & Why

Results on the held-out test set:

| Model | Test MAE | vs Baseline |
|-------|----------|-------------|
| Median baseline | 213.9 s | — |
| Ridge regression | 90.2 s | 2.4× better |
| **HistGradientBoostingRegressor** | **74.2 s (~1.2 min)** | **2.9× better** |

**The gradient boosting model won.**

Why? Trip duration is not a straight-line problem. The data has interactions like:

- rush-hour congestion gets worse for longer trips
- long trips hit highway slowdowns
- rain slows long trips more than short ones

A linear model like Ridge can only draw straight lines. Gradient boosting builds many small decision trees that can bend around those interactions, so it predicts more accurately.

## Monitoring, Drift & Retraining

Real ML models degrade over time as the world changes. This project simulates that.

### How to simulate drift

```bash
.venv/bin/python scripts/simulate_drift.py
```

This script:

1. Loads the clean validated trips.
2. Uses the champion model to predict durations on them (reference window).
3. Creates a "shifted" window:
   - moves every pickup to 17:30 (evening rush)
   - stretches trip distances by 40%
   - inflates actual durations by 30% (congestion)
4. Predicts on the shifted window with the same champion model.
5. Writes `monitoring/drift_report.json`.

Result:

```
reference MAE  = 73.4 s
shifted MAE    = 155.7 s   ← much worse
MAE change     = 2.12×
```

### Then decide

```bash
.venv/bin/python scripts/run_retraining_check.py
```

It outputs:

```json
{
  "data_valid": true,
  "severe_drift": true,
  "performance_degraded": true,
  "action": "retrain_and_compare"
}
```

The decision is a recommendation, not an automatic action. A human would then retrain the pipeline and promote the new model only if it beats the old one.

## What Is Missing / Next Steps

| Area | Next Step |

| **Monitoring** | Expand drift checks to more features and add a dashboard/alerts. |

data → clean → features → train → compare → serve → monitor → recommend retrain

It uses common production-style tools but keeps everything small and local — exactly what a POC should do.
